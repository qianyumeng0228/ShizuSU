## 7. 建议的同步策略（不要一次性 merge）

**Stage 0 · 冻结与备份（半小时级）**
- 推送未推的 `c1dd5700`；打标签 `shizusu-sync-base-20261110`；另建 `sync/upstream-20261110` 工作分支，`feature/module-submission` 保持可发布。

**Stage 1 · 只取安全与内核正确性（低风险、高价值）**
- 以 cherry-pick 方式取：`e67b14e6` `85d05cf2` `9dd165e8`（SELinux 策略）、`56bba12f` `e1ea5dad`（avtab）、`dfae9237`（回滚校验）、`d58ff8d7`（init.rc bind-mount）、`7ef2dbb7`（服务阶段重复触发）、`45fab659` `8f6d140e`（原子路径日志）、`e17a48a7`（symtab 搜索）、`708f083c`（文件引用平衡）。
- 每条单独编译 + 真机 `su -c id`、模块加载、隐藏自检后再下一条。

**Stage 2 · 内核结构对齐（高风险，需决策）**
- 决策点：是否接受上游 `kernel/extension/` 中枢，把我们 `dynamic_manager`/`stealth`/susfs 通道迁进去，并退役 `kernel/manager/dynamic_manager.c`。
- 若接受：先做“上游功能等价性核对”（读对照：我们的签名表 vs 上游 `manager_identity.h` + 动态管理器；命令号 25/26/106/107 vs 扩展 ioctl），再按命令点逐个移植，最后才删旧文件。
- 若不接受：放弃整包合并，改为长期 cherry-pick，代价是每次上游改 `dispatch.c` 都要手工重放。

**Stage 3 · 用户态 ksud**
- `cli.rs`/`module.rs` 已是我们重排过的版本，建议以上游新版为底，把我们新增子命令（模块管理、susfsd）以**追加**方式重建，而不是双向合并文本。

**Stage 4 · Manager 功能按需移植（先挑对我们痛点有用的）**
- 优先移植：`674aa00c`（无限滚动+预览按需，替代我们已回退的分页）、`9246a1c6`（自定义镜像）、`c4aef682`（应用内更新保留 APK）、`3f17fc7a`（Long versionCode 的安装状态）。
- 明确不移植（保持 ShizuSU 自有体系）：多源主题商店系列（20+ 提交）、模块仓库切 KernelSU Modules API（`a3397a24`）、Material/Miuix 全局重设计（会摧毁我们现有的卡片与详情视觉）。
- 语言包（约 50 个 `strings.xml`）：不做文本合并；以**上游语言包为底**，把我们新增的键以独立命名空间（如 `shizusu_*`）追加进去，避免键冲突。

**Stage 5 · 收尾**
- 全量 `git merge upstream/main` 只在前四阶段完成后尝试；剩余冲突应集中在 docs 与少量 UI 文件。
